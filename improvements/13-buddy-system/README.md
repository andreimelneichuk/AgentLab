> **v2 (фикс scope-бага, не промпта):** baseline SR=10% (худший из всех

> каталоге это ломало **197 из 753 ходов (26%)**, каждое срабатывание
> добавляло лишний retry с LLM-вызовом judge (латентность) и портило

> проверка, для которой session-wide scope осознанно сохранён. Также убран
> дублирующийся мёртвый код и двойной `continue` (та же категория багов,
> что чинили в 05/07/09/10/11/12). См. IMPLEMENTATION.md.

## Иллюстрация проблемы

AI-ассистент для письма: в начале следует стилю, через несколько ходов — «общий AI-язык» (тире, рваные фразы, пустые переформулировки).

Та же механика в серьёзных сценариях:

- Compliance-проверки пропускаются
- Support flows теряют обязательные шаги
- Tool schemas «размываются» к середине сессии

Это частный случай **дрейфа промпта** (см. 06), но с **активной коррекцией**, а не только превентивным SCAN.

## Паттерн Buddy System

```
Main Agent (worker)
  — рассуждает, вызывает tools, генерирует ответ

Buddy Agent (напарник)
  — наблюдает output worker
  — если пропущен шаг / неверный tool / дрейф → Guide с feedback
  — worker отбрасывает ответ и повторяет

После max_retries → пропустить (не зациклиться)
```

**Ключевая установка:** дрейф **неизбежен** — проектируй систему коррекции, не надейся на вечное следование промпту.

## Результаты (AWS, 3000 прогонов)

| Подход | Точность |
|--------|----------|
| Только промпт | 82.5% (~1 из 5 провалов) |
| Buddy / Steering | **100%** на 600 прогонах |

Дополнительно: −66% input-токенов vs длинные SOP в промпте, −47% output-токенов.

**Нюанс:** на мощных моделях в коротких задачах разница мала. Выигрыш — **длинные сессии** и слабые модели.

## Реализация (Steering Handler)

```python
# Концепт Strands Agents SDK
def steering_handler(worker_output, criteria) -> Guide | None:
    if not meets_criteria(worker_output, criteria):
        return Guide(feedback="Пропущен вызов get_policy_fact перед [POLICY_OK]")
    return None  # pass
```

Worker получает Guide и **повторяет**, зная конкретную ошибку.

## Критерии для Buddy (Baseline Agent)

- Вызван ли обязательный tool перед маркером ответа
- Нет ли forbidden tool в trace
- Сохранён ли формат вывода (Секция 4)
- Для instruction-сценариев: выполнены ли явные шаги из `s09_instruction`

## Что менять в Baseline Agent

| Место | Действие |
|-------|----------|
| `buddy_agent.py` | Judge prompt + criteria registry |
| `agent_core.py` | Loop: generate → judge → retry |
| Критерии по тегам | `critical` → строгий buddy |

## Критерии успеха

- `s09_instruction`, `s10_adversarial` → 100% на ранее flaky ходах
- Сравнение с 06 SCAN: buddy ловит drift **после** генерации, SCAN **до**
- max_retries соблюдается, нет infinite loops

## Комбинация с 06

| SCAN | Buddy |
|------|-------|
| Превентивный (до задачи) | Реактивный (после output) |
| Дешёвый (~300 токенов) | +1 полный judge call |
| Восстанавливает attention | Проверяет соответствие |

Рекомендация: SCAN на каждый critical ход + Buddy на финальный ответ.
