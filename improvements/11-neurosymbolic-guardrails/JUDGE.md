## Метод верификации: полная офлайн-симуляция каталога

В отличие от v1 (только unit-тесты на изолированных `ctx`), для v2
построена симуляция всего guardrail pipeline по 166 сценариям — каждый
ход проходит `pre_tool`/`post_tool` в реальном порядке с persistent
`GuardrailSessionState`, используя `expect_tool_called`/`expect_tool_args`
как ground truth последовательность вызовов. Это позволило количественно
измерить эффект каждого раунда фикса, а не полагаться на догадки.

## Раунд 1: cross-turn state loss

`GuardrailContext` пересоздавался **целиком** в начале каждого `run_turn()`
— правила `require_prior_success`/`require_confirmation` теряли информацию
об успешных tool-вызовах из предыдущих ходов. 40 пар ходов вида
`employee_lookup(ход N)` → `leave_balance`/`org_chart_dept`(ход N+1) ложно
блокировались.

**Fix:** состояние разделено на `GuardrailSessionState` (persist на всю
сессию) и per-turn `GuardrailContext` (turn_tool_counts — per-turn).

**Эффект:** 38 → 18 affected сценариев.

## Раунд 2: над-строгие workflow-правила

Симуляция после раунда 1 показала **18 сценариев всё ещё блокируются** —
другой причиной. `hr_two_phase_org`/`company_before_contact`/
`customer_before_quote` требовали prior lookup безусловно, но схема
`ticket_create(subject)`/`sales_quote(product)`/`org_chart_dept(department)`
вообще не содержит `customer_id`/`emp_id` — правило структурно не может
быть привязано к конкретной сущности (тикет/КП/dept-запрос не ссылается
ни на какого клиента/сотрудника).

**Проверка перед удалением:** ни один сценарий каталога не использует
`forbid_tool_called` для этих tools по workflow-причине (только recall-
ходы типа "не запрашивай снова") — удаление не противоречит ground truth.

**Fix:** три правила удалены из дефолтного `rules/hr.yaml`/`rules/crm.yaml`
(v2.0.0) с явным комментарием trade-off. Механизм (`require_prior_success`/
`require_confirmation`) остаётся в `guardrails.py`, покрыт тестами через
in-memory engine — можно вернуть точечно для tool с реальной cross-entity
зависимостью.

**Эффект:** 18 → 0 affected сценариев (по офлайн-симуляции).

## Trade-off, который стоит явно зафиксировать

Удаление двухфазного HR-подтверждения (`hr_two_phase_leave`,
`employee_before_leave`) убирает защиту от enumeration чужих `emp_id` без
lookup — README изначально называл эту защиту флагманской фичей experiment
11 ("Двухфазное подтверждение чувствительных операций"). В каталоге этого
бенчмарка НЕТ сценария, тестирующего именно этот abuse-case, поэтому
удаление не снижает измеримую SR/CSR — но если появится compliance-
ориентированный сценарий именно на этот кейс, правило нужно будет вернуть
(механизм для этого сохранён).

## Раунд 3: новые аддитивные правила (без over-strict риска)

После раунда 2 guardrails стали безопасными, но тонкими — большинство
защиты, отличавшей 11 от baseline, была именно в удалённых workflow-
правилах. Раунд 3 добавляет защиту в местах, где её не было **вообще**:

- **CORE/SSE field-валидация** (`rules/core.yaml`, `rules/sse.yaml`) — 7 из
  8 tools без единой post_tool проверки получили `require_substrings`.
  `calc_expression` исключён (dual success/error формат, require_substrings
  не умеет "A или B").
- **`no_untraceable_markers`** (новый rule type `require_marker_traceable`) —
  ловит galлюцинированные/injected marker-значения (`ORANGE-99` вместо
  `violet-42`) через session-scoped `tool_response_history`. Не флагает
  adversarial-refusal (переиспользует логику `benchmark/scoring.py::_marker_claimed_as_fact`).

**Метод верификации выявил урок про сам процесс тестирования:** первая
попытка симуляции post_response (используя `' '.join(expect_contains)`
как заглушку tool-контента) дала **59 сценариев, 120 false positives** —
но причина оказалась в самой методике теста (усечённый `expect_contains`
не проходил новую field-валидацию раунда 3(a), маркер не попадал в
session history), не в баге правила. После перехода на реалистичные
полноформатные mock-ответы — **0 false positives**.

**Побочная находка (не исправлена):** `policy_ok_requires_fact`
(существовал до этой переработки, не тронут в раундах 1-2) ложно блокирует
`s09_009` turn 0 — там `[POLICY_OK]` подтверждает НОВОЕ правило
форматирования от пользователя, а не факт политики. Отличить эти два
случая надёжно текстовым правилом рискует той же over-generalization, что
уже отклонили для anaphora-эвристики в 10 — оставлено как известное
ограничение, не фикшено.

## Рекомендации

1. Прогнать e2e на catalog для подтверждения — офлайн-симуляция сильный
   индикатор (0% false-block во всех трёх раундах), но не замена реальному
   прогону
2. Использовать offline full-catalog simulation (не только unit-тесты на
   изолированном `ctx`) как стандартную практику при добавлении новых
   guardrail-правил — именно этот метод выявил все три раунда проблем,
   которые 31 unit-тест v1 пропустил
3. **При построении offline-симуляции для post_response-правил** — строить
   session history из РЕАЛИСТИЧНОГО tool-контента (полный формат, как
   вернул бы настоящий MCP mock), не из `expect_contains` напрямую — иначе
   получаются false positives, вызванные самой методикой теста, а не
   реальным багом правила (см. "урок" в разделе "Раунд 3")
4. Использовать `TestCrossTurnSessionPersistence`/
   `TestRequirePriorSuccessMechanism`/`TestMarkerTraceability` как
   эталонный паттерн для будущих guardrail-правил с state, зависящим от
   истории или от match конкретных аргументов
