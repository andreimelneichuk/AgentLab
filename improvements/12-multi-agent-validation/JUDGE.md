## v3: три направления, реализованные через параллельных агентов

Пользователь запросил улучшение уже исправленного (v2) подхода. Три
направления реализованы тремя параллельными агентами на **непересекающиеся
новые файлы** (репозиторий не git — без worktree-изоляции конкурентные
правки одного файла были бы риском повреждения; интеграция в
`agent_core.py`/`validator_agent.py` сделана человеком после, серийно).

### 1. Tier-1 символическая проверка (`symbolic_precheck.py`)

Пункты 2-5 чеклиста валидатора (`prompts/validator_system.txt`) — tool
trace, консистентность фактов, формат, STOP-политика — не требуют LLM,
это ровно то, что уже реализовано детерминированно в эксперименте 11
(`guardrails.py`). `symbolic_precheck()` (самодостаточная адаптация, без
импорта из соседнего эксперимента) вызывается ПЕРЕД LLM-валидатором — при
найденном нарушении LLM не вызывается вообще. LLM остаётся только для
пункта 1 ("соответствие запросу") — генуинно семантической проверки.

**Найденный при интеграции нюанс:** trace накапливается по ВСЕЙ истории
хода (не только текущая попытка) — значит decoy/hallucination-нарушение
из попытки 1 продолжает блокировать tier-1 на всех retry, даже если
retry не повторяет тот же вызов явно. Это защитное поведение (нельзя
"вылечить" нарушение просто переформулировав текст) потребовало
пересмотра одного из regression-тестов v2, который неявно предполагал
обратное.

### 2. Production-совместимый триггер (`risk_signals.py`)

**Ключевая находка:** старый механизм (`validator.is_enabled_for_tags(scenario_tags)`)
принципиально не переносится в продакшен — `scenario_tags` это тестовая
метаинформация, которой в реальном использовании просто негде взяться.
`detect_risk_signals()` анализирует содержание хода (policy-контекст, tool
error, side-effecting tool, финансовые значения, adversarial-паттерны,
маркер без backing tool) — работает без scenario_tags.

**Офлайн-замер на реальном каталоге** (753 хода): **22.7%** триггер-рейт
с реалистичным tool_trace — разумный масштаб, не взрывной рост
(изначальный замер без tool_trace показал искажённые 32.5%, скорректировано
методологией). Активация валидатора теперь = tag OR risk-signal, старое
поведение полностью сохранено как подмножество нового.

### 3. Структурированный retry-feedback

`ValidationResult.reasons`: `List[str]` → `List[ValidationReason(code, detail)]`
с полной обратной совместимостью (`_coerce_reason`, переопределённый
`__eq__` для сравнения со строками — существующие v1/v2 тесты не менялись).
`format_retry_feedback()` даёт worker'у конкретную подсказку по коду
(`tool_not_called` → "Вызови обязательный инструмент...") вместо общей
фразы. Промпт валидатора обновлён с описанием кодов, обратная
совместимость парсера со старым string-форматом сохранена.

## Процесс верификации

Каждый агент запустил тесты внутри своей задачи (16+21+22 = 59 тестов на
момент завершения агентов). После интеграции полный прогон (66 тестов)
выявил **3 упавших теста** — не из-за багов в новом коде, а потому что
существующие v2 test-фикстуры использовали неполную структуру `messages`
(только `tool_call_details` без `result`/`status`, без реальных
assistant-tool_calls/tool-role записей) — это заставляло
`build_tool_trace()` уходить в неполный fallback-путь, который
непреднамеренно триггерил новые tier-1 проверки. Все три теста
переписаны на реалистичную структуру `messages` (как реально формирует
`_run_worker_turn`), один тест (`test_pipeline_preserves_forbidden_tool_call_from_rejected_attempt`)
дополнительно пересмотрен по семантике — decoy-нарушение теперь корректно
продолжает блокировать retry, пока данные в контексте, что оказалось
более защитным поведением, чем изначально предполагал тест v2.

Дополнительно измерен reality-check `risk_signals.py`'s trigger rate на
реальном каталоге ДО интеграции — обнаружена и исправлена методологическая
ошибка (пустой tool_trace завышал rate до 32.5% против реалистичных 22.7%).

## Незакрытые пункты (перед full production)

- [ ] E2E бенчмарк на `localhost` для подтверждения
  улучшения SR/CSR — офлайн-верификация (66 тестов + reality-check на
  каталоге) даёт высокую уверенность, но не заменяет реальный прогон
- [ ] Метрика "validator catch rate на synthetic false success" (пункт
  чеклиста README, открыт с v1) — не закрыт
- [ ] `risk_signals.py`'s `marker_without_matching_tool` не имеет
  session-wide контекста (только текущий ход) — над-триггерит на
  recall-ходах; компенсируется tier-1's session-wide traceability
  (не создаёт ложных REJECT, только лишние — но бесплатные — проверки)
