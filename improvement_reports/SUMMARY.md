**Метрики:**
- **SR** — Solve Rate: доля сценариев, где все ходы прошли
- **CSR** — Critical Solve Rate: SR только по критическим сценариям
- **TA** — Turn Accuracy: доля успешных ходов
- **TSA** — Tool Selection Accuracy: насколько точно выбирается нужный инструмент
- **AH** — Anti-Hallucination: агент не выдумывает факты без MCP
- **lat** — средняя латентность на ход

## Описание подходов и результаты

### original — Baseline (SR=26%, AH=57%)

Эталонный агент без изменений. Хорошо выбирает инструменты (TSA=95%), но слабо цитирует их ответы в тексте — отсюда низкий SR. Антигаллюцинация 57% — агент иногда выдумывает факты когда MCP недоступен.

---

### 01 — Four-section prompt (SR=32% ↑, лучший)

**Идея:** системный промпт разделён на 4 чётких секции — роль, правила работы с инструментами, формат ответа, запреты. Убирает размытость инструкций.

**Результат:** единственный вариант лучше baseline по всем ключевым метрикам. SR вырос с 26% до 32%, TSA почти идеальный (96%), точность ходов TA=54%. Подтверждает: структура промпта критична даже без изменения логики агента.

---

### 02 — Tool validation layer (SR=14% ↓)

**Идея:** перед каждым вызовом инструмента агент валидирует аргументы по схеме — отклоняет невалидные вызовы до отправки в MCP.

**Результат:** SR упал вдвое. Дополнительный слой валидации создаёт трение: агент реже решается вызывать tools (TSA упал до 69%), что ломает сценарии где tool обязателен. Подход правильный, но реализация слишком строгая для данной модели.

---

### 05 — Deterministic routing (SR=14% ↓)

**Идея:** вместо того чтобы LLM сам решал какой инструмент вызвать, добавляется детерминированный маршрутизатор по ключевым словам запроса.

**Результат:** TSA=64% — маршрутизатор работает хуже самой модели в выборе инструментов. Жёсткие правила не покрывают разнообразие формулировок из бенчмарка.

---

### 06 — Scan prompt drift (SR=11% ↓, lat=4.9s)

**Идея:** агент периодически «пересканирует» системный промпт в процессе диалога, чтобы не забыть инструкции при длинном контексте.

**Результат:** самый медленный из простых вариантов (в 6.7x дольше baseline). TSA упал до 44% — дополнительные пересканирования путают модель. Проблему prompt drift решает неэффективно.

---

### 07 — Focus active compression (SR=12% ↓)

**Идея:** активная компрессия истории диалога — старые ходы сжимаются/суммируются, чтобы уменьшить context bloat.

**Результат:** хуже baseline по всем метрикам. Компрессия теряет важные детали из прошлых ходов, которые нужны для recall-сценариев (а их в бенчмарке много).

---

### 08 — Semantic tool selection (SR=11% ↓)

**Идея:** вместо показа всех 25 инструментов агент сначала семантически ищет подходящие и получает только топ-K.

**Результат:** TSA=56% — худший показатель выбора инструментов. Семантический поиск ошибается в фильтрации: нужный инструмент не попадает в топ-K и агент его не видит.

---

### 09 — Context engineering (SR=13% ↓, lat=1.1s)

**Идея:** специальная инженерия контекста — скретчпад для рабочих заметок агента во внешнем хранилище, структурированная история.

**Результат:** TA=23% — один из худших по точности ходов. Overhead на управление скретчпадом перевешивает пользу от структурированного контекста.

---

### 10 — Subtask isolation (SR=15% ↓)

**Идея:** длинный диалог разбивается на изолированные подзадачи, каждая решается в отдельном мини-контексте.

**Результат:** небольшое улучшение abstention (71%), но SR=15%. Изоляция подзадач мешает recall через несколько ходов — агент не видит результатов предыдущих подзадач.

---

### 11 — Neurosymbolic guardrails (SR=21%, TSA=86%)

**Идея:** жёсткие программные guardrails поверх LLM — символические правила запрещают нарушения (нельзя вызвать decoy-инструмент, нельзя ответить без MCP при наличии инструмента).

**Результат:** лучший abstention (83%) и хороший TSA (86%). SR=21% — выше многих вариантов. Guardrails правильно ловят нарушения, но иногда блокируют валидные ответы. Потенциально сильный подход при тонкой настройке правил.

---

### 12 — Multi-agent validation (SR=11% ↓)

**Идея:** второй агент-валидатор проверяет ответ первого перед отдачей пользователю — ловит функциональные галлюцинации.

**Результат:** CSR=12% — критические сценарии провалились почти полностью. Валидатор слишком часто отклоняет правильные ответы или сам ошибается. Двойной агент увеличивает latency и вводит новый источник ошибок.

---

### 13 — Buddy system (SR=10% ↓, lat=5.6s)

**Идея:** «напарник» — параллельный агент следит за дрейфом стиля и инструкций, периодически корректирует основного.

**Результат:** худший SR (10%) и самая высокая латентность (5.6x от baseline). TSA=36% — buddy путает основного агента своими коррекциями. Подход создаёт больше проблем чем решает.

---

### 14 — Graph RAG (SR=24%, CSR=49%, lat=0.82s)

**Идея:** вместо чистого векторного поиска — граф знаний с верификацией фактов. Агент отвечает только если факт найден в графе, иначе говорит «не знаю».

**Результат:** второй по CSR (49%), хорошая латентность. SR чуть ниже baseline, но критические сценарии решает лучше. AH=55% — граф помогает ловить галлюцинации. Перспективный подход, особенно для compliance-задач.

---

### 15 — Memory formation (SR=26%, CSR=54%, AH=61% ↑)

**Идея:** персистентная семантическая память между сессиями — важные факты из разговора сохраняются и используются в следующих диалогах через векторный поиск.

**Результат:** SR на уровне baseline, но **лучший AH (61%)** и **лучший CSR (54%)**. Память помогает не выдумывать факты и лучше справляться с критическими сценариями. Самый перспективный вариант для production-использования.

---

## Топ-3 рекомендации

1. **Внедрить** `01 — Four-section prompt` как минимальное улучшение без риска — даёт +6pp SR при нулевых накладных расходах
2. **Исследовать** `15 — Memory formation` для production: лучшая защита от галлюцинаций и критических провалов
3. **Пересмотреть** `11 — Neurosymbolic guardrails`: идея правильная, но правила нужно смягчить чтобы не блокировать валидные ответы
