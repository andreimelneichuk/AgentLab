# 06 — Метод SCAN (против дрейфа системного промпта)

**Tier:** 2  
**Источник:** Nikolasi, DEV Community / OpenAI Community (февраль 2026)  
**Проблема:** Через 30+ минут агент «забывает» системный промпт — инструкции теряют вес в attention

## Механизм проблемы

Системный промпт — токены в **начале** контекста. При росте окна их относительный вес падает:

| Контекст | Доля внимания на промпт |
|----------|-------------------------|
| 2 000 токенов (1K промпт) | ~50% |
| 80 000 токенов (1K промпт) | ~1% |

Инструкции «вымываются» — не деградация модели, а математика attention.

## Почему не работают простые фиксы

| Подход | Проблема |
|--------|----------|
| Повтор промпта каждые N сообщений | 2000+ токенов, пассивное чтение слабее генерации |
| Перезапуск сессии | Потеря накопленного контекста |
| Суммаризация | Помогает recall фактов, **не** восстанавливает вес правил |

## Метод SCAN

**Идея:** заставить модель **генерировать** токены, связанные с инструкциями (~20–300 токенов), а не пассивно перечитывать промпт.

### Шаг 1 — Маркеры в промпте

В конце каждого раздела system prompt:

```
...правила обработки данных...
@@SCAN_1: Какие данные затронет эта задача? Что если стейт устарел?

...обработка ошибок...
@@SCAN_2: Какой наиболее вероятный сценарий сбоя?
```

### Шаг 2 — Триггер перед задачей

Агент отвечает на маркеры в **output** (не только в thinking):

```
SCAN_1: Задача затрагивает сессию. Риск двойного списания при устаревшем стейте.
SCAN_2: Таймаут внешнего API без retry.
```

### Шаг 3 — Постпроверка CHECK/MISSED

```
CHECK: сброс сессии ✓, коды ошибок ✓
MISSED: конкурентные запросы — ок, задача однопоточная
```

### Шаг 4 — Уровни

| Уровень | Токены | Когда |
|---------|--------|-------|
| FULL | ~300 | Критические задачи |
| MINI | ~120 | Средние |
| ANCHOR | ~20 | Между подзадачами |
| SKIP | 0 | Тривиальные операции |

## Критичное требование

Ответы SCAN должны быть в **видимом output** модели, не только во внутреннем reasoning — именно генерация восстанавливает attention.

## Смежные эффекты

- Защита от prompt injection (правила безопасности снова «тяжёлые»)
- Удержание схем API в фокусе
- CHECK/MISSED для оркестратора в multi-agent

## Практика автора

- 11 агентов, контекст 100K+, 7 маркеров
- Стоимость < 0.5% от всех токенов
- Без SCAN — потеря правил к середине сессии

## Что менять в Basic

| Место | Действие |
|-------|----------|
| `prompts/system_master.txt` | Добавить `@@SCAN_N` в конец секций 1–3 |
| `agent_core.py` | Хук: перед сложным ходом — SCAN-триггер |
| Orchestrator | Уровень SCAN по тегу сценария (`critical` → FULL) |

## Критерии успеха

- `s09_instruction`, `s10_adversarial` — стабильное следование правилам на ходах 10+
- Не рост `over_call` из-за лишних рассуждений
- Overhead токенов < 1% на полном каталоге
