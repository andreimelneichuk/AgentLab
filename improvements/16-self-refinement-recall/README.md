# 16 — Dynamic Prompting and Self-Refinement (recall omission)

**Tier:** 2
**Источник:** emergentmind.com, статья про context degradation в LLM-агентах,
раздел "Dynamic Prompting and Self-Refinement" (техника: модель перепроверяет
собственный черновик ответа против исходного запроса/контекста и
переписывает его, если обнаруживает, что не ответила по существу) +
методология этого репозитория (см. `improvements/12-multi-agent-validation/`,
чей Tier-1/Tier-2 gating scaffolding здесь расширен).

## Проблема

Техники 11 (neurosymbolic guardrails), 12 (multi-agent validation) и 13
(buddy system) ловят **fabrication** — агент СТРОГО УТВЕРЖДАЕТ что-то
неверное в ответе (decoy tool выдан за источник, false success после
ошибки инструмента, `[POLICY_OK]` без реального факта, untraceable marker).

Есть другой, не менее вредный режим отказа context degradation — **omission**:
агент не говорит ничего ложного, он просто **молча не включает** в ответ
конкретное значение, которое пользователь явно просит напомнить/уточнить и
которое было установлено РАНЕЕ в разговоре (EMP_ID сотрудника, `POLICY_FACT=`,
маркер вида `violet-42`, тир клиента, названное предпочтение языка
программирования и т.п.). В длинных сессиях (context degradation: contex
window заполняется шумовыми ходами между установлением факта и recall-
вопросом о нём) это особенно вероятно — агент технически "видит" факт в
истории, но не связывает его с текущим вопросом и отвечает мимо цели, не
солгав ни разу.

`benchmark/scenarios/catalog/s14_drift_recall.yaml` — прямая иллюстрация:
10 фактов устанавливаются в начале 50-ходового диалога, 27 ходов шума, затем
11 ходов строгого recall с `forbid_tool_called` (нельзя перевызывать
инструмент) и `max_tool_calls_delta: 0`. Не-fabrication ответ вида "Не могу
сейчас точно сказать" на такой вопрос технически не лжёт — но проваливает
`expect_contains`.

## Концепция: Tier-1 gate → Tier-2 self-refine

```
Worker draft answer
       │
       ▼
detect_likely_omission(user_message, history, draft_answer)   ← Tier-1, бесплатно
       │ triggered?
   нет │              да
       ▼               ▼
  return draft   ОДИН доп. LLM-вызов: build_refine_prompt()
                  (черновик + вопрос + явный указатель на
                   пропущенный факт из истории) → скорректированный
                   полный ответ
                        │
                        ▼
                  return refined answer
```

Tier-1 срабатывает только если ОДНОВРЕМЕННО выполнены три условия:

1. **(a) Recall-намерение.** Сообщение пользователя похоже на
   recall/reference-вопрос: явная фраза ("напомни", "какой у меня", "что я
   говорил", "шаг N", "в начале разговора") ИЛИ местоимение/анафора
   (он/она/это/тот/такой) в сочетании с вопросительной формой, ИЛИ
   собственное первое лицо в вопросе ("какой язык я предпочитаю?").
2. **(b) Найден релевантный кандидат в истории.** В более раннем сообщении
   диалога есть конкретное значение (`KEY=VALUE`-маркер, `word-digit`-маркер
   вида `violet-42`/`EMP-4242`/`C-GOLD-001`, число после `=`, названное
   предпочтение, ISO-дата), чей контекст пересекается по ключевым словам
   (proper noun/ID/число/дата) с текущим вопросом.
3. **(c) Значение отсутствует в черновике.** Значение (или его "голая"
   форма без `KEY=` для `KEY=VALUE`-кандидатов) не встречается в
   `draft_answer`.

Как и в 10-subtask-isolation (`is_recall_turn()`), чистая
pronoun/anaphora-эвристика была явно рассмотрена и НЕ используется в
одиночку — там она давала 11-18% false positive на задаче "нужен ли вообще
tool call". Здесь задача другая (не блокировка tool call, а решение о
ДОПОЛНИТЕЛЬНОМ LLM-проходе после уже готового черновика), поэтому
местоимение допустимо — но только как один из путей в условие (a), и
только вместе с (b)+(c), которые сами по себе редко выполняются
одновременно на обычных ходах. Численно это даёт false positive rate
0.67% на нерекольных ходах реального каталога (см. IMPLEMENTATION.md).
