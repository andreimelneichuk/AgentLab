# Judge Report — 13-buddy-system (v3)

**Триггер:** реальный e2e benchmark-прогон измерил `antiHall=66%(39/59)
lat=4.38s` для 13 — худшее antiHall И худшая латентность среди всех 13
вариантов (baseline `antiHall=86%(51/59) lat=1.17s`). Это прямое
противоречие v2-заметке "ожидается заметно выше SR / заметно ниже
latency" (см. незакрытый пункт "E2E бенчмарк ... для подтверждения" ниже
в v2-отчёте) — v3 разбирает почему ожидание не подтвердилось.

## Hypothesis A (latency) — ПОДТВЕРЖДЕНА

Чтение `agent_core.py::run_turn()` показало: `judge_worker_output()`
вызывался на каждой buddy-итерации, и внутри него дорогой LLM-вызов
исполнялся **безусловно**, если `symbolic_precheck` не находил
нарушения — а `symbolic_precheck` ловит только 2 узких паттерна
(forbidden tool, missing `[POLICY_OK]`), так что LLM вызывался
фактически на каждом ходе (офлайн-подтверждено: 753/753 на каталоге).
Это ровно та ошибка, которую 12-multi-agent-validation уже решил своим
Tier-1/Tier-2 гейтом — 13 никогда не получал такой гейт, потому что в
v2 пользователь **явно отклонил** gating в пользу "always-on, но менее
агрессивно" (задокументировано в v2-отчёте ниже). Измеренная
latency-регрессия (4.38s) заставила пересмотреть это решение в v3.

**Fix:** `buddy_agent.detect_llm_judge_risk()` — Tier-1 гейт (regex/
множества, без LLM), адаптация `risk_signals.py` из 12. LLM теперь
вызывается только при сигнале риска (незаземлённый маркер/сумма/tool
error/policy-контекст/adversarial). Structural always-on сохранён —
`symbolic_precheck` (дешёвая часть) по-прежнему выполняется на КАЖДОМ
ходе, гейтится только дорогой LLM-шаг.

**Офлайн-верификация (753 хода, 18 файлов каталога):** LLM-вызовы
753/753 → **85/753 (−88.7%)**; false-positive rate не регрессировал —
**остался 0/753**.

## Hypothesis B (recall) — ЧАСТИЧНО ПОДТВЕРЖДЕНА (не через промпт)

Проверка кода опровергает буквальную формулировку гипотезы: `BUDDY_JUDGE_SYSTEM`
**не менялся** в v2 (v2-отчёт ниже явно это фиксирует — фикс был целиком
в scope `symbolic_precheck()`, не в промпте LLM-judge). Значит "промпт
стал менее агрессивным" — не то, что произошло буквально.

Реальный, независимый от v2 источник recall-риска: `BUDDY_JUDGE_SYSTEM`
чеклист был целиком про tool-usage/format/decoy — **ни одного пункта**
про grounding фактов в TOOL_RESULT. Даже когда LLM вызывался безусловно
(v2), у него не было явной инструкции ловить фабрикацию цифр/ID/сумм.

**Fix:** (1) явный grounding-пункт добавлен в `BUDDY_JUDGE_SYSTEM`; (2)
тот же сигнал незаземлённости — Tier-1 триггер гейта, так что "нужно
позвать LLM" и "LLM явно ищет фабрикацию" теперь совпадают структурно.

**Верификация recall:** 3 параметризованных unit-теста (fabricated
salary/marker/ticket-no-tool-call) — 3/3 триггерят гейт. Офлайн-инъекция
незаземлённого маркера `REF-9999` в draft_answer каждого из 753 ходов
каталога — **753/753 (100%) триггерят гейт**.

**Известное ограничение (задокументировано, не скрыто):** Tier-1 гейт
заточен под marker/ID/сумма-формы фабрикации (доминирующие в каталоге и
в 11/12 test suites). Чисто словесная фабрикация без числового паттерна
по-прежнему может проскочить гейт (тот же trade-off, что в 12).

## Контекст решения (важно для дальнейшей работы)

Пользователь явно рассматривал и **отклонил** вариант с gating (по
аналогии с `risk_signals.py` из эксперимента 12 — не звать buddy на
низкорисковых ходах). Инструкция: **"этот компонент будет всегда работать
но может просто промт ему написать менее агрессивным при этом будет
следить чтобы системный промт соблюдался"** — компонент должен оставаться
always-on, задача — снизить false-positive rate, не покрытие.

Ключевой инсайт при разборе: агрессивность была НЕ следствием строгости
промпта LLM-judge — она была следствием **бага в символической (не-LLM)
проверке**, которая всегда идёт первой. Промпт `BUDDY_JUDGE_SYSTEM`
не трогался вообще — фикс полностью на уровне кода `symbolic_precheck()`.

## Найденная и исправленная причина

**Session-wide vs per-turn scope в symbolic_precheck().** Проверки "вызван
ли `get_policy_fact`"/forbidden tool использовали `trace` = **вся история
сессии**, а не текущий ход. `get_policy_fact`, вызванный в ходе 1, требовал
`[POLICY_OK]` в ЛЮБОМ последующем несвязанном ходе (например про погоду).

**Подтверждено на реальном каталоге:** 197 из 753 ходов (26%) ложно
блокировались. Каждое срабатывание = 1 лишний LLM-вызов judge (объясняет
худшую латентность 5.62s) + навязанный бессмысленный тег на корректном
ответе (объясняет худший SR 10%).

**Fix:** добавлен `current_turn_trace` параметр — trace **только текущего
хода**. `_tool_names_from_trace` (forbidden tool + policy_ok-after-fact
проверки) теперь работает на этом scoped trace. Полный `trace` (вся сессия)
**осознанно сохранён** для ЕДИНСТВЕННОЙ проверки — детекции персистентного
правила диалога, явно установленного пользователем — это не баг, это
корректный by-design session-wide кейс.

**Верификация:** 3-этапная офлайн-симуляция по каталогу (197 → 25 → 0),
где промежуточный этап (25) подтвердил, что остаточные срабатывания — не
баг, а корректная работа правила на упрощённой тестовой заглушке ответа
(без реального тега, который добросовестный агент бы добавил).
